# デモシナリオ — 自宅の屋根をトークナイズし、購入・運用・監視する

**推奨：3分40秒の提出動画。対面デモでは20秒を操作の予備時間に使う。**

ユーザーの四つの体験を軸にする。

1. **自分の資産をトークナイズする**
2. **他人の資産の権利を購入し、事業に参加する**
3. **所有するトークンを運用する**
4. **ダッシュボードで運用を監視する**

サンプルは「東京に家を持つAさんが、屋根を太陽光事業に使うために権利を売り出す」。①は所有者A、②〜④は購入者Bに切り替え、同じ案件を追う。自分で発行した権利を自分で買うデモにしない。

公式案内では提出動画は2〜4分、対面審査はデモ4分＋質疑3分。待ち時間の編集は認められるが、倍速化やAI音声は使用しない。録画は本人のナレーションで行う。[ETHGlobal Tokyo 2026案内](https://ethglobal.com/events/tokyo2026/info/details)

この文書は台本と準備手順。人間による通しリハーサルと録画は未実施。

## サンプル：東京の家の屋根を売りに出す

「屋根の権利」の中身を二つに分ける。家の所有権を売る設定ではない。

| 権利                       | 誰が持つか          | できること                                                  | デモでの位置づけ                                                |
| -------------------------- | ------------------- | ----------------------------------------------------------- | --------------------------------------------------------------- |
| **屋根の利用権**           | 太陽光設備の運営者  | 定めた期間・用途で屋根を使う。排他的な利用なら1口           | ①で対象空間・用途・期間を説明する。利用権と収益権は別のトークン |
| **太陽光事業の収益分配権** | 購入者Bなどの参加者 | その権利のVaultへ実際に入金された収益を口数に応じて受け取る | ①で発行・出品し、②で購入、③で受取・再出品、④で状況を確認する    |

本編で操作する中心は**収益分配権**。利用権は準備済みの別権利として示すか、条件説明に留める。両者を作成済みと説明する場合は、それぞれの実在するright IDを確認する。

Tokenizeのタイトル例は **Tokyo Home Solar Roof · Demo**。概要は「この屋根に太陽光設備を設置し、設備・施工費を募り、運営から入金された収益を持分に応じて分配する」。すべて架空の住宅・事業とテスト通貨による例。

## 覚えてもらう一文

> 「自分の空間を事業にし、他の人が権利を購入し、保有後の収益と運用状況まで追えるようにします。」

英語の締め：

> “Tokenize your space. Back someone else's project. Manage your rights and track what happens.”

冒頭または最初の資産詳細に **Fictional project · Test tokens · Simulated real-world verification** を表示する。権利の売買はテストネットの実取引、所有権や現地稼働の審査は模擬、という区別を一度は声で説明する。

### ③「運用」で実際に見せる操作

1. 対象の収益権がActiveで、購入者Bが10/100口を保有した後に、運営側が10,000 mJPYを入金する。この準備過程も録画し、Bが受け取る前に短く見せる。
2. Bの **My assets → 1,000 mJPY claimable → Claim revenue**。受取後に請求可能額が減ったことを確認する。
3. **Resale / redeem quantity: 2**、**Resale price per unit (mJPY): 1000** を設定して、対象権利の **List for resale**。承認・出品後に **Your open listings** を見せる。
4. 「2口を出品した」と説明する。この市場は出品時に権利を預託しないので、未約定なら保有は10口のまま。売れた・2,000 mJPYを受け取った・残り8口になったとは説明しない。

2口が実際に売れるところまで見せる場合だけ、別の購入者Cで約定し、Bの残高8口と受取額を確認する。この操作は時間が増えるため質疑用に回す。

**バスケット組成は延長版。** もう一つの互換性のある収益権を事前に保有し、Compose → Save basket plan → 対象バスケットのAdd your rights → Deposit rights & receive sharesまで行う。「組合せを保存した」だけで資産を運用したことにはしない。担保借入・貸付利息は未実装。

**再分割を主役にする場合：** ③の再出品を、Markets → Fractional → 取得済み収益権1口を預託して1,000持分を発行 → 250持分の出品へ置き換える。Cの購入後に入金した収益は持分に応じて配分される。貸出は別の利用権と役を要するため、質疑用に回す。追加2コントラクトを公開接続するまでは「Local Anvil / Real contract transactions」と表示し、公開ネットワークの取引と混同しない。

| 見る場所                                   | 観察するもの                                   | 次の判断・操作                                                 |
| ------------------------------------------ | ---------------------------------------------- | -------------------------------------------------------------- |
| **My assets**                              | 自分の保有口数、請求可能額、出品状況           | 収益受取、保有継続、一部の再出品                               |
| **Dashboard / Market activity**            | 一次販売・二次流通・バスケットの約定額         | 資金募集と流通を区別する。再出品だけでは出来高は増えない       |
| **Dashboard / Follow the deposited money** | 市場全体の入金・引出し                         | 入金が実際にあるか確認。残高を自分だけの請求可能額とは読まない |

## 分割・貸出の実装範囲

③の「運用」には取得後の再分割・期限付き貸出も実装した。実装済みと公開接続済みを分けて説明する。

| やりたいこと                             | 現状                                                               | 屋根の例                                                           |
| ---------------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------ |
| **最初から収益権を小口で発行**           | 実コントラクトで可能。ERC-1155の供給量を設定する                   | 100口を発行し、Bが10口を購入する                                   |
| **保有分の一部だけ売る**                 | 実コントラクトで可能。数量指定の出品・部分約定                     | Bの10口のうち2口を売りに出す                                       |
| **取得済みの1口をさらに細分化**          | FractionVaultで実預託・持分発行・売買・収益・償還を実装。AnvilでUI検証済み、公開接続待ち | 屋根の収益権1口を預け、1,000持分にする。排他的利用権は分割対象外 |
| **期間付きの利用権を最初に発行**         | 実コントラクトで可能。発行者がscope・用途・開始・終了を定義する    | 指定期間に屋根を太陽光用途で使う権利。排他的利用は1口              |
| **保有トークンを貸して後で返してもらう** | RentalEscrowで預託・前払い貸出・自動失効・早期返却・回収を実装。AnvilでUI検証済み、公開接続待ち | Bが利用権をescrowへ預け、Cが期間だけ利用する。期限後にBが原資産を回収 |
| **担保にして資金を借りる／利息を得る**   | 未実装                                                             | 屋根トークンを担保にした借入や貸付利息は発生しない                 |
| **複数の収益権をまとめる**               | BasketVaultで原資産の預託・持分発行・償還を実装                    | 屋根Aと屋根Bの互換性のある収益権をまとめる                         |

小口購入と、取得済みのトークンの再分割は別の操作。期間付き利用権の発行と、保有者による一時貸出も別の操作。

実ウォレットモードではMy assetsの`Split / rent rights`から実コントラクト用Marketsへ進む。設定不足なら接続未完了を表示する。`/demo`にある`Fractionalize / lend · mock`は従来のmock creditsによる別シミュレーションで、元の権利トークンは移動しない。

分割対象はOpen譲渡の収益権。貸出対象はOpen譲渡の排他的利用権。貸出料金は前払い・早期返却の返金なしで、元の権利の有効期間を超えられない。ENSの発行権限委任はこの貸出とは独立しており、借り手に新規発行権限を与えない。

実装参照：[FractionVault.sol](../contracts/src/FractionVault.sol)、[RentalEscrow.sol](../contracts/src/RentalEscrow.sol)、[RightsFinance.tsx](../src/components/RightsFinance.tsx)。再現コマンド・MultiBaas利用箇所・公開接続手順は[追加機能の実装記録](FINANCE_IMPLEMENTATION.md)を参照。

### 主役・アカウント・数値を固定する

| 項目         | 推奨設定                                                                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 案件         | 屋根の太陽光事業を一件。公開CurvegridではKanda等の既存案件から在庫を確認して選ぶ。Sepoliaで一本化する場合は`Chiyoda ENS Solar Roof · Test` |
| 登録者       | 資産を登録し、権利・委任を管理するウォレット                                                                                               |
| 運営者       | ENSとアプリ両方の許可を受け、登録者のために権利を発行する別ウォレット                                                                      |
| 購入者       | 対象権利をまだ保有していない別ウォレット。ガスとMockJPYを用意                                                                              |
| 審査担当     | デモ用verifier。登録者と同一アドレスの場合は独立審査と説明しない                                                                           |
| 発行条件の例 | Revenue Share / Rooftop / SOLAR / 有効な期間 / 発行100口 / 1口1,000 mJPY                                                                   |
| 購入の例     | 10口＝10,000 mJPY。一次募集が100口なら、その募集の販売進捗は10%                                                                            |
| 入金の例     | 購入後に10,000 mJPYをdeposit。新規購入者の請求可能額は1,000 mJPY                                                                           |
| ENS委任の例  | 発行許可200口→100口を発行→残り100口がある状態で取消。上限消化と取消の効果を区別できる                                                      |

ENSの既存検証報告は**10口の発行**。この報告を見せる場合は「100口発行した」と読み替えない。200口の委任等は次の収録用の提案値であり、実行済みの設定ではない。

### 概要欄の読み上げ例

> 「屋根に太陽光設備を設置して運営する計画です。募集資金は設備と施工に使い、契約条件に沿って、事業から入金された収益を持分に応じて分配します。」

事業計画には、対象顧客、発電・売電の想定、設備設置、保守、入金の責任者とリスクを記載しておく。試算欄を見せる場合は「編集できる仮定」と説明する。未調査の発電量や試算上の利回りを実績として読まない。

### 撮影前に済ませる操作

- 地図タイル、対象案件、ENS証拠、購入txのタブを事前に読み込む。案件を探す時間を本編に入れない。
- アプリのURL、チェーン、アセットID、right ID、listing ID、取引hashを控える。別のチェーンの同じIDと混同しない。
- 登録者・購入者・運営者は分かる名前を付けたブラウザプロファイルで分ける。実ウォレットでDemo roleを使わない。
- 資産と権利の承認、必要な出品在庫、開始時刻、購入者のガス・MockJPYを確認する。準備済みの承認は冒頭で短く示す。
- ENSの権利は委任発行直後には審査待ち。承認してから出品する。資金募集の完了だけではActiveにならない。
- Revenue部分では稼働状態を確認し、**購入完了後**に新しい入金を作ってからclaimする。購入前にあった収益は以前の保有者に帰属する。
- Claim映像を撮る前に残高と請求可能額を記録する。一度claimした額を再度受け取れる前提で撮り直さない。
- Dashboardには実際に件数がある次の操作を用意する。対象がゼロなら、その項目をクリックする台本は使わない。
- ユーザーの既存データをResetせず、収録用の状態を準備する。公開チェーン全体の数値を「この一件の実績」として読まない。

## ENSの役割をどう説明するか

①の「自分の屋根をトークナイズする」で、**空間の識別と、運営者への発行権限の委任**として説明する。

| 役割                           | このプロジェクトでの動き                                                                                                                        |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **どの空間かを識別する**       | `rooftop.building-1.chiyoda.tokenizetokyo-demo-2026.eth`の階層で屋根・建物・地域を表す。登録済み名をasset ID・scope・権利コントラクトへ紐付ける |
| **誰が関与できるかを管理する** | 所有者役の登録者が運営者へENSの名前単位のロールを与える。発行コントラクトが現在のロールを確認する                                               |
| **委任範囲を制限する**         | ENSロールに加え、自作のUrbanNamespaceAuthorityが用途・期間・発行数量等の許可を確認する。ENSだけで数量上限が決まるわけではない                   |
| **委任を取り消す**             | 必要なENSロールまたはアプリの発行許可を取り消すと、新たな委任発行を止める。既に購入された権利や発生済みの収益は没収しない                       |

本編の短い説明：

> 「この名前は、どの建物の屋根かを示します。登録者は、この屋根についてだけ運営者に発行を任せられます。ENSの権限と、こちらの契約で定めた用途・期間・数量を発行時に確認し、許可を取り消せば新たな発行は止まります。」

「名札」の説明だけで終わらず、**許可があると発行でき、取り消すとできない**という結果を見せる。これがプロダクト上の役割になる。

技術説明を求められたら、ENSで使うロールは名前単位の`ROLE_SET_RESOLVER`であり、アプリの発行許可は別の`grantIssuance`だと説明する。ENSに標準の「屋根の利用権」「100口の発行枠」が備わっていると表現しない。発行物は登録者へ届き、別途verifierの承認を必要とする。

ENSの発行権限委任は、購入者のトークンを第三者へ貸す操作ではない。名前の登録も物件の所有権証明ではない。コード：[UrbanNamespaceAuthority.sol](../contracts/src/UrbanNamespaceAuthority.sol)、[createScopedRightForIssuer](../contracts/src/UrbanRightToken.sol#L139)。詳細：[ENS設計](ENSV2_DESIGN.md)。

## ENSを①の中で見せる／40秒の補助映像

本編の①では約20秒で登録済み空間、限定発行、取消の結果を示す。以下は補助映像の40秒構成で、本編へ追加して4分を超えないようにする。Tokenizeから新規登録した全資産にENS名が自動登録される実装ではない。現在のENS対象は紐付け済みの屋根サンプルを使う。

### 公開UI接続後の推奨カット

1. **0–8秒：空間を特定。** ENS Indexで登録済み屋根を開き、`Registered space · Sepolia`、asset ID、scopeを映す。長い名前は全て読み上げず、`rooftop → building → district`を指す。
2. **8–18秒：限定委任。** 登録者が`Operator wallet address`と`Maximum units`を入力し、確認チェック→`Delegate roof issuance`。ENSロールとアプリの発行上限という二つの許可を与える。
3. **18–28秒：実際に発行。** 運営者で`Units to prepare`→`Prepare rights for the issuer`。登録者に権利が届き、残り発行枠が減った結果を映す。
4. **28–40秒：取消。** 登録者で`Revoke operator permission`。運営者側を再読込し、発行不能になった状態を映す。検証記録で、取消後の発行がコントラクトにも拒否されることを添える。

署名と承認待ちは実際に完了させ、その待機部分だけを編集で短縮する。UIでのボタン無効化だけをコントラクトの拒否証拠と呼ばない。別空間を発行するUIは用意されていないため、内装・別資産の拒否は検証結果を補助証拠にする。

## 対面4分への置き換え

本番中に一から登録・二段階の審査・ENS委任・購入・入金・claimを全て実行すると、署名と承認待ちだけで時間を使う。

- ①は準備済みの下書き・承認・発行結果を使い、登録者として行った操作を説明する。②の購入を本番のライブ操作の中心にする。ウォレット接続・ガスを先に整える。
- ENSの複数トランザクションと収益分配は、短い録画または事前実行の結果として明示して見せる。
- ②の購入枠を超えても待機し続けない。購入がPendingならその状態を伝え、準備済みの取引証拠へ移る。
- 最後の20秒は索引反映や画面切替の予備時間。3分40秒で内容が終わる読み上げ速度を一度測る。

## 質疑で見せる追加機能

- **排他的利用の競合：** 同じ屋根・重複期間の排他的用途を追加すると拒否。収益持分の非排他的な権利まで一律に競合すると説明しない。
- **Basket：** 互換性のある収益権を預けて持分を受け取る。裏付けのcustodyと償還を示す。計画の保存だけでは持分は発行されない。
- **再販売：** 売却代金は売る保有者へ。一次募集と分け、以前に発生した収益は売り手に残ることを説明する。
- **新規登録：** TokenizeのSpace → Right → Publish、資産承認と権利承認の区別を通しで見せる。
- **未実装範囲：** 実物件の所有権審査、募集未達時の自動返金、実円の入出金等は[信頼モデル](TRUST_MODEL.md)を参照。

再分割・貸出・Basketを本編ですべて操作しない。③では一つを選び、残りは質疑用に回す。審査員が一件の「権利・お金・権限」の流れを追える長さにする。
