> **ピッチの勝敗を決める1問**
>
> *「可視化はすごい。で、トークン化したことで具体的に何ができるようになったの？」*
>
> **答え：** 同じ屋上の同じ年数を二人に売ることができなくなり、見知らぬ100人がそのキャッシュフローを共同で持てるようになり、収益はトークンの持ち主に自動でついていく。これを個別契約ではなくコードが強制する。
>
> - **競合の拒否（Scene 3）：** 期間が重なる排他的な屋上の権利を二つ目として発行すると「Spatial Right Conflict」で失敗する（`UrbanRightToken.findConflict`、`verifyRight` で再チェック）。
> - **購入 → 稼働（Scene 4）：** Investor B が収益権を購入。テストJPYの支払いとERC-1155の受け渡しが1トランザクションで決済される（`UrbanMarketplace.purchase`）。Verifier が稼働させると屋上が緑に変わる。
> - **Activity 台帳：** AssetVerified、RightCreated、ListingPurchased、RevenueDeposited を MultiBaas の Event Query から表示。Curvegrid Testnet 上にスクリプト実行の448トランザクション（資産50、権利44、売買69、収益入金20）がある。

## I. トークンと現実の権利

**Q1. 具体的にどの権利をトークン化しているのか？** [A]
建物ではない。権利＝空間×時間×用途×キャッシュフロー。資産ID、正規スコープ（屋上・内部・壁面・土地・全体）、半開区間 `[start, end)` の期間、種類（利用・収益分配・賃借・その他）、用途、規約ハッシュ、移転ポリシーの組み合わせ。1つの権利が供給量固定のERC-1155 IDになる。排他的な利用権は供給量1、収益権は分割できる単位。
根拠：`UrbanRightToken.RightRequest`、`createScopedRight`

**Q2. トークン保有者はどんな法的権利を持つのか？** [A]
このプロトタイプでは何も持たない。資産は架空で、Mock JPY に価値はない。設計上は、トークンがオンチェーンにハッシュを刻んだ規約文書を指し、利用権の保有者はそこに書かれた利用を、収益権の保有者は実際に入金された額の按分を受け取る。コードが保証するのは分配の計算と移転ルールまで。規約を所有者に対して法的に執行できるようにする仕組みは、まだ作っていない。
根拠：`Right` の `termsURI` と `termsHash`、`RevenueVault.claim`

**Q3. NFTを移転したら不動産の所有権も移るのか？** [A]
移らない。トークンは建物の所有権を一度も表していない。移転されるのはスコープ付きの権利（例：屋上太陽光の10年分の収益）で、登記には一切触れない。画面にも「Map data does not prove ownership. No residential or property ownership is sold.」と出している。

**Q4. 登記簿とオンチェーンの保有者が食い違ったら、どちらが正しいのか？** [A]
不動産の所有権については、常に登記簿が正。チェーンが正なのはもっと狭い範囲で、誰がどの権利トークンを持ち、何が支払われ入金されたか。発行者が実は所有者でなかった場合、Verifier が資産を否認するか権利を終了させる（`verifyAsset(id,false)`、`closeRight`）。

**Q5. 現実の権利とトークンの対応は誰が保証するのか？** [A]
`VERIFIER_ROLE` の保有者。デモではデプロイヤーが持っていて、検証は模擬。本番では司法書士や信託会社などの資格を持つ第三者が、登記記録と規約を確認する。コントラクトはすでに資産の検証と権利の検証を分けていて、同じ正規位置ハッシュで検証済みにできる資産は1つだけ。
根拠：`UrbanAssetRegistry.verifyAsset`、`verifiedAssetByGeo`、`UrbanRightToken.verifyRight`

**Q6. 所有者の同意なく「Dormant（休眠）」とラベルを付けてよいのか？** [B]
現時点で実在の物件には何もラベルを付けていない。Opportunity Lens の約150地点は生成したデモ用の点で、「Demo dataset · not real listings」と表示している。プロトコル上の「Dormant」は所有者が登録した資産のライフサイクル段階で、「まだ権利が発行されていない」という意味にすぎず、建物について何かを主張するものではない。本番でも個別地点のラベルは所有者が登録した資産だけに付け、未登録の供給は公的統計と投資家の関心表明のレベルにとどめる。
根拠：`src/lib/dormant.ts`（`DORMANT_DATASET_LABEL`）、`src/lib/lifecycle.ts`

**Q7. 家・土地・スペースが本当に空いている、使われていないとどう証明するのか？** [B]
物理的に空いていることをオンチェーンで証明はしないし、そう主張もしていない。所有者が提供する余力を申告して根拠資料を出し、権利の発行前に Verifier が審査する。チェーンが証明するのは「その余力がまだ誰にも約束されていない」こと。検証済みの排他的な権利があれば、期間が重なる権利は発行できない。

**Q8. PLATEAUで本当にその情報が取れるのか？** [A]
取れないし、使ってもいない。PLATEAU は3D都市モデルで、建物の形状と一部の属性を持つが、所有者や空き状況は記録していない。私たちの地図は MapLibre と OpenStreetMap / OpenFreeMap のタイル。PLATEAU は、将来より細かい建物形状を得るためのデータ源の候補にとどまる。

**Q9. 資産価値や期待利回りは誰が見積もるのか？** [B]
意図的にプロトコル内では誰も見積もらない。発行者が出品価格を決め、市場が受け入れるかどうかを決める。収益はオペレーターが実際に入金した分だけで、アプリは利回りを約束していない。評価オラクルが必要になるのは担保貸付からで、これが次のレイヤー。
根拠：`UrbanMarketplace.createListing`（価格は売り手が設定）、`RevenueVault.depositRevenue`

## II. 規制

**Q10. KYC/AMLはどうするのか？** [A]
未実装。プロトタイプはテスト通貨しか使わない。本番では登録業者やパートナーがKYC/AMLを行い、権利を Allowlist ポリシーで発行して、承認されたアドレスしか送受信できないようにする。一次販売の購入もすべての移転と同じチェックを通る。
根拠：`UrbanRightToken._update`、`setAllowed`

**Q11. そのトークンは金融商品ではないのか？** [A]
法的な分類は断定しない。移転可能な収益分配トークンは、金融商品取引法上の電子記録移転権利や集団投資スキーム持分にあたる可能性がある。だからプロトタイプでは架空の資産と価値のない Mock JPY だけを使い、現実のものは何も売っていない。実運用は登録業者と弁護士を通す。

**Q12. 不動産特定共同事業法や金商法との関係は？** [A]
どちらも関係しうるが、どちらについても結論は言わない。収益分配権は金商法の論点になり、不動産に投資するために資金を集めると不動産特定共同事業法の論点になる。本番の道筋は、登録業者やパートナーを通じて運営し、適格性は Allowlist で、必要な利用権は Nontransferable で管理すること。

**Q13. 自由に売買できるERC-20で問題ないのか？** [B]
権利はERC-20ではなく、権利ごとに移転ポリシーを持つERC-1155。ERC-20なのは支払い用トークンだけ。「Open」はテストネット用で、本番の投資型の権利は Allowlist、特定のオペレーターから動かしてはいけない利用権は Nontransferable にする。

**Q14. 海外投資家への販売制限はどうするのか？** [B]
どの制限がかかるかは弁護士が判断することで、ここでは言わない。どんな制限でもKYCと同じ仕組みで執行する。仲介業者が `setAllowed` の前に適格性を確認し、許可されていないアドレスは権利を受け取れない。

**Q15. 許可制の移転はどう実装しているのか？** [B]
すべての移転で `_update` が権利のポリシーを確認する。Open は通過、Allowlist は送り手と受け手の両方が `allowed[id]` に入っている必要があり、Nontransferable はリバートする。Nontransferable の権利は取引可能扱いにならないのでマーケットに出品できず、バスケットに入れられるのも Open の収益権だけ。
根拠：`UrbanRightToken._update`、`isTradable`、`isBasketCompatible`

## III. トークン化後の運用

**Q16. 収益は誰が回収し、誰がオンチェーンに送るのか？** [B]
オペレーター、たとえば屋上の太陽光事業者。オフチェーンで収入を回収し、`depositRevenue` を呼ぶ。これは権利が Active で期間内のときしか通らない。この役割向けのサーバー側 Cloud Wallet 経路は実装済みだが、本番環境ではまだ動かしていない。オンチェーンの20件の入金はスクリプトで実行したもの。

**Q17. 賃料や利用料が支払われなかったら？** [B]
入金がなければ保有者の受け取りもゼロ。約束した利回りがないので、破られる約束もない。未払いは公開される。その期間の Activity 台帳に RevenueDeposited が出ない。オペレーターからの回収は規約に基づいてオフチェーンで行い、Verifier は権利を終了させられる。

**Q18. 物件が売却されたらトークンはどうなるのか？** [A]
オンチェーンでは自動では何も変わらない。権利は `endAt` まで、または Verifier が終了させるまで続く。新しい所有者がその権利に拘束されるかはオフチェーンの契約で決まり、その法的な設計はまだ作っていない。トークンだけで売却後も権利が残る、とは主張しない。

**Q19. 所有者がトークン化をやめたくなったら？** [B]
売った単位を取り戻すことはできない。そこが肝心な点。所有者にできるのは、手元に残った単位のバーン、マーケットでの買い戻し、`endAt` を待つこと。稼働中の権利を終了させると取引と新しい入金は止まるが、すでに発生した収益は引き続き請求できる。
根拠：`burn`、`closeRight`、`RevenueVault.claim`

**Q20. トークン保有者はどう出口を取るのか？** [C]
デモ場面：Portfolio → 保有銘柄の **List for resale**。保有者なら誰でも単位の一部または全部を `UrbanMarketplace` に出品でき、部分約定もできる。バスケット保有者は **Redeem** で原資産の権利に戻せる。テストネットのスクリプト実行では69件の売買に二次流通の購入も含まれている。

**Q21. 流動性がないならRWAの意味はあるのか？** [B]
流動性は保証しないし、約束もしていない。流動性がなくても残る価値は、同じ空間の二重販売がないこと、誰でも小口で共同保有できること、収益が自動で保有者についていくこと、支払い履歴が公開されていること。バスケットは複数の屋上をまとめるので、1つの屋上より需要の幅が広い。

## IV. プロダクトそのものへの攻撃

**Q22. 普通の不動産クラウドファンディングで良いのでは？** [A]
クラファンは1つの物件を丸ごと、1社のファンドで資金調達し、記録もその会社のデータベースにある。私たちは1つの建物をスコープ付きの権利に分ける。屋上を10年、1階を週末、それぞれに別のキャッシュフローがあり、プラットフォームをまたいで売買やバンドルができる。登録済みのクラファン事業者は、競合というより自然なパートナーで販売チャネルになる。

**Q23. なぜデータベースではなくブロックチェーンなのか？** [A]
当事者が多く、誰も1社のデータベースを信用していない。所有者、Verifier、オペレーター、多数の投資家、バスケット保有者。チェーンは誰もこっそり書き換えられない3つのルールを強制する。排他利用の重複禁止、支払いと受け渡しの同時決済、実際の入金だけからの収益按分。データベースでもルールは表現できるが、自社が運営していないマーケットや Vault に守らせることはできない。オフチェーンでの別契約までは止められず、止められるとは主張しない。

**Q24. 既存のREITで良いのでは？** [B]
REITは大きく安定した物件を丸ごと持つ。小さな屋上の10年分や、空き家の週末利用は買えない。私たちが狙うのは、既存の器には小さすぎ、部分的すぎ、期間が限られすぎている余力。

**Q25. 「休眠資本」の問題は本当に存在するのか？** [B]
公的統計にある。都内の空き家は89.7万戸、うち賃貸・売却・二次利用のどれでもない「その他の空き家」が21.4万戸、空き家率10.9%（総務省、2023年）。23区の未利用地は約1,303ha（東京都、2021年）。戸建住宅の太陽光設置率は約6.0%（東京都、2022年度）。

**Q26. 市場規模とその数字の根拠は？** [B]
TAMは出さないし、作ることもしない。引用している数字は供給量を測るもので、空き家、未利用地、太陽光のない屋根、それぞれ出典は政府の調査。需要は、次に作る関心表明機能で測る。

**Q27. 最初の顧客は誰か？** [A]
契約済みの顧客はまだいない。これははっきり言う。最初のターゲットは屋上で、都心区のビル所有者と太陽光事業者の組み合わせ。2025年4月からの東京都の太陽光義務化は大手事業者の新築住宅が対象なので、既存の屋根は空白のまま残る。需要が先。投資家が関心を示し、アプリ・代理店・紹介で所有者に届け、検証し、需要が見えている状態でトークン化する。

**Q28. 誰がお金を払うのか？** [B]
予定しているのは一次発行と決済への手数料で、プラットフォームか運営する登録パートナーが受け取る。現在のコントラクトは手数料を取らず、ビジネスモデルは未実装。

**Q29. 資産所有者がトークン化する動機は？** [B]
物件を売ったり丸ごと貸したりせずに、空間の余力で稼げること。2026年の国交省公表で23区の住宅地価は+9.0%、5年連続の上昇で、所有者は売らずに持ち続けたい。この仕組みなら、持ち続けながら屋上や週末を収益化できる。資金は一次販売で先に入る。

**Q30. 投資家が買う動機は？** [B]
特定の屋上や空間のキャッシュフローに小口で参加できる。これは既存の商品にない。入金も請求もすべて公開台帳に残り、単位は転売もバスケットへのバンドルもできる。利回りの約束はなく、収益は入金された分だけ。

## V. スポンサー技術 / Curvegrid

**Q31. なぜCurvegridが必要なのか？** [A]
コントラクトのためではなく、プロダクトのため。RWAの市場はライフサイクル履歴で成り立つ。誰が検証したか、いつ稼働したか、何が支払われたか。MultiBaas はそれを自前のインデクサやDBなしで提供する。`add` 集計付きの Event Query、ユーザーのウォレットで署名する未署名トランザクションの生成、私たちのロールに合うRBACのキー。スクリプトの448トランザクションはすべて MultiBaas で生成した。Webhook、Cloud Wallet、TXM は実装済みだが本番環境では未実行。

**Q32. MultiBaasなしでも作れたのでは？** [B]
作れる。自前のインデクサ、バックエンド、鍵管理を用意すればよく、MultiBaas が既にくれたものを作り直すことになる。統合はロゴだけではない。位置指定の `inputIndex`、1ページ50行の上限、残高のある送信者を要求するガス見積もりなど、7つの具体的な問題に当たって直し、フィードバックとしてまとめた。
根拠：README「(e) Experience with MultiBaas」

**Q33. 「ダッシュボード」はただの3D可視化では？** [C]
デモ場面：購入後の **Activity**、続けて **Dashboard**。すべての行が MultiBaas の Event Query から来たオンチェーンのイベントで、取引量と収益入金の合計はサーバー側の `add` 集計を使っている。テストネットの台帳にはスクリプトの448トランザクションが載っている。

**Q34. 「トークン化」はただのNFTミントのデモでは？** [C]
デモ場面：**Scene 3 の競合拒否**。単純なミントは何でも通すが、私たちのものは検証されていない発行者、期間が重なる排他的な権利、分割された排他的な権利を拒否する。ミントの後にも、全移転での移転ポリシー、購入後の収益だけを受け取るためのチェックポイント、カストディで裏付けたバスケットがある。丸め誤差のファズテストを含む25本の Foundry テストで検証している。

## VI. デモの信頼性

**Q35. 本当に東京の不動産をトークン化しているのか？** [A]
していない。資産はすべて架空、検証は模擬、Mock JPY に価値はなく、現実の物件は何も売っていない。本物なのはプロトコル。6つのコントラクトが Curvegrid Testnet（chain 2017072401）にデプロイされ、MultiBaas に索引され、448トランザクションがチェーン上にある。

**Q36. 資産が架空なら、何を証明したのか？** [A]
仕組みを、稼働しているチェーン上で証明した。競合判定エンジン、同時決済、按分の収益インデックス、固定比率のバスケット、移転ポリシー、2段階検証。読み取り専用のスクリプトで Event Query の集計と突き合わせている。証明していないのは、現実の需要、法的な執行力、実際の所有権確認。この線引きは毎回言う。

**Q37. 本当に3Dである必要があるのか？** [C]
デモ場面：日本橋 Solar Roof で **City X-ray**。ここでの権利は縦に重なる。屋上・内部・壁面・土地は同じ敷地の中の別の空間。平面の地図では1本のピンに潰れてしまうが、3Dならどの層が埋まっていてどの層が空いているかが見える。

**Q38. Googleマップのピンと何が違うのか？** [C]
デモ場面：**Opportunity Lens → Rooftop**、そして稼働後に屋上が緑になる瞬間。ピンは場所を示すだけ。ここでは各空間がオンチェーンの状態を持つスコープ付きの権利を持っている。Dormant、Funding、Funded、Active。地図が変わるのは、コントラクトの状態が変わったから。

**Q39. なぜチェーンに載せると休眠資産が動き出すのか？** [A]
チェーンだけでは動かない。チェーンが取り除くのは、小さな余力が眠ったままになる理由。今は空間の一部を売るのにも物件全体についての個別契約が要る。屋上の10年分が、二重販売できず保有者に自動で支払う標準の単位になれば、資金を集められる大きさになる。それでも稼働には所有者、オペレーター、需要が要る。だからコールドスタートは需要から始める。

**Q40. 「発見」と「資金調達」の間には実務上の大きな溝があるのでは？** [B]
ある。だから両端を作った。発見側（Lens、X-ray）と資金調達側（検証、同時決済、収益、バスケット）。その間をつなぐのが関心表明で、投資家の需要を所有者に届ける。これが次に作る機能。その後に、実際の検証パートナーと、KYCを前提にした Allowlist での移転が続く。

## 答えられない質問が来たら

1. まず模擬のものを言う。資産、所有権の検証、Mock JPY、デプロイヤーが持つ Verifier ロール。
2. 何がいつ出るかを順番で言う。次は関心表明。その後に検証パートナーと Allowlist によるKYC。担保貸付は評価オラクルと法務レビューの後。ENSv2 はローカルアダプタがテスト済みで、Sepolia へのデプロイは未了。Webhook の配信、Cloud Wallet、TXM は実装済みで本番環境では未実行。
3. 法的な分類は絶対に断定しない。「金商法の対象になりうる。だからテスト通貨と架空の資産で回避している。本番は登録パートナーを通す」。
4. 検証済みリスト以外の数字は出さない。TAMも出さない。
